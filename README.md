APEX 是面向 DeepSeek Harness 的任务增强插件。我们围绕工具调用、任务协作和结果验证构建执行环境，探索基础模型在实际交付中的能力边界。

## 我们在做什么

项目围绕一个核心问题展开：**在保持基础模型不变的前提下，更合适的工具、协作方式和反馈，能否提高完整任务的通过率？**

APEX v1.0 将这项研究落成了可安装的插件：模型可以使用官方工具完成工作，按需要组织团队，并通过浏览器检查、只读审查和执行记录核验结果。任务如何分解、是否委派、何时检查，仍由模型结合任务和用户要求决定。

我们同时维护插件实现与对照实验，分别回答“工程机制是否正确运行”和“最终作品是否更好”这两个问题。

## 为什么这样做

在已完成的四冲程柴油机任务中，两组作品都能生成复杂场景，也都报告过自测通过；进一步检查却发现了机械装配、运动关系或交互稳定性上的错误。这说明，本案例中的自测与展示没有覆盖完整验收要求。

因此，APEX 的开发重点是：

- **让模型能够实际执行和检查。** 使用文件、命令、浏览器及协作工具，把判断建立在可观察结果上。
- **按任务需要组织工作。** 简单任务直接完成，有独立子任务时再使用团队协作。
- **用完整交付衡量收益。** 同时记录任务通过率、质量、严重故障、耗时和资源消耗，判断额外开销是否值得。

## v1.0 已经做出了什么

| 方向 | 当前实现 |
| --- | --- |
| 原生工具执行 | 从首轮使用官方 PTC（通过程序调用工具），组合文件、搜索、Shell、Web 和后台任务能力。 |
| 按需团队协作 | 复用官方 Teams 的成员、消息、任务依赖、取消与恢复机制，补充 APEX 的协作指引和状态诊断。 |
| 浏览器验证与证据 | 在独立无头浏览器中执行指定交互，检查页面状态、DOM 和截图；可读取实际工具执行记录。 |
| 可选只读审查 | 调用仅具备读取能力的审查子代理，提供有依据的发现和后续检查建议。 |
| 执行与取消保护 | 在 macOS 上实现会话私有临时目录、受限写入与进程信号保护；阻止取消后的自动通知继续触发模型请求。 |
| 可分发的插件 | 仓库包含 v1.0 安装入口、预设、回归测试、开发文档，以及首轮对照论文与脱敏资料；最终 v0.2.0-rc.2 适配随封存上传。 |

PTC、文件、Shell、Web 和 Teams 的基础能力来自官方 Harness。APEX 的工作集中在这些能力的组合、调用指引、验证工具和必要的执行保护上；各项机制的效果仍需通过实验分别评估。

### 工程验证

- **此前版本的模式隔离回归已通过。** 该历史检查覆盖 macOS 上的同进程模式切换、APEX/PTC 并发、Minimal 持久终端、截图读取、审批、取消和清理；没有调用付费模型。
- **当前 0.2.0-rc.2 已完成源码同步、官方构建核验与 macOS 桌面加载。** APEX 完整回归 363/363、官方相关检查 114/114 通过；347 个客户端构建产物摘要一致。四项 peer 与官方运行时匹配，未使用版本豁免。已安装官方桌面应用可加载自定义 APEX，在实际会话中执行 PTC、文件和 Bash，并展开命令结果。组件回归包含模式隔离、Teams、取消、工作区保护与真实无头浏览器检查；这些检查不代表模型收益。Linux/Windows 真实宿主验证仍未完成。
- **9 月 30 日补齐两个执行入口。** `workspaceOnly` 可按明确的工作区列表启用；`apex_run_script` 的字面 `argv` 入口保留被启动程序的退出状态，后续打印在 PTC 中进行。相关回归 87/87、最终完整回归 379/379 通过；冻结作品重放 57/57，错误断言副本 56 通过、1 失败并退出 1。本批为零真实模型调用的组件验证，未重新加载正在运行的桌面实例。普通 Bash 和程序内部自行吞错仍需独立验收，见[使用说明](docs/APEX-1.0.md)。
- 安装、挂载、重复安装、错误拒绝、取消和资源清理已有对应检查。具体范围见 [发布验证记录](docs/PUBLICATION.md)。

### 首轮复杂任务对照

我们使用同一模型配置（`deepseek-flash / max`）完成四冲程柴油机三维交互任务，对照官方原生环境与 APEX v1.0。两组各生成一次，按同一套 37 项量表检查冻结的实际交付。

| 指标 | 官方原生对照 | APEX v1.0 |
| --- | ---: | ---: |
| 原始得分（满分 100） | 72.8 | 83.8 |
| 应用严重故障上限后的得分 | 40.0 | 83.8 |
| 完整任务验收 | 未通过 | 未通过 |
| 完成时间 | 51 分 13.9 秒 | 26 分 44.6 秒 |
| 全会话树输出 token | 265,713 | 1,229,906 |

原生对照因渲染冻结和关键机械连接缺陷触发严重故障上限。APEX 样本得分较高、完成较快，但仍有装配偏移、局部运动及信息一致性问题，输出 token 约为对照的 **4.63 倍**。

**这是一项探索性的单任务观察。** 每组仅一次生成、评价非盲、运行顺序固定且总计算预算不等，尚不能证明稳定、普遍或因果性的能力提升。

## 封存时的研究进度

**APEX 在 v1.0 正式集成及后续效果评估后停止开发。** 以下保留最后阶段的完成项与研究限制；未完成的验证不再列为继续开发的承诺。

- **已完成：** v1.0 插件集成、历史公开记录、macOS Web 验证、当前 0.2.0-rc.2 工程适配与官方桌面实测，以及 B–C 可靠测量、D 候选动作研究和 E 两项新任务的修复范围对照。
- **E 的采用决定：** 在完整 APEX 内固定初稿和失败事实，比较一般复查与局部根因修复，共四次预定运行。固定功能集合均通过，但局部组只在区间任务较快；库存任务耗时更长，且漏交 README 和最终说明。未达到事先采用门槛，保留可选，不追加本批付费重复。详见[当前验证记录](docs/PUBLICATION.md#阶段-e跨任务采用决定)。
- **后续问题：** 优先处理完成状态与实际交付不一致、Shell 退出状态和最终说明的已知缺口；只有明确变化能够影响采用决定时，再安排新的对照。研究结项不代表稳定收益已证明。
- **平台待办：** 补充 Linux / Windows 真实 Harness 主机验证。当前真实宿主实测范围包括历史 macOS Web 与本轮官方 macOS 桌面工具执行。

后续评估将以**完整任务通过率**为主要指标，并同时报告质量、严重故障、耗时和分类用量。

## 使用与进一步了解

封存包名为 `dsh-apex@1.0.1`，预设为 `apex-v1`，选择器名称为 **APEX 1.0.1**；固定兼容基线为 **DeepSeek Harness v0.2.0-rc.2**。最终源码保存在本仓库，未发布到 npm。1.0.1 用于标识最后一轮对照实验的实现，实验同时记录源码摘要。恢复时请按文档核对对应的官方构建与依赖版本。

**APEX 是与官方 PTC、Minimal 并列的独立模式。** 安装后可在同一个 Harness 进程中选择和同时使用不同模式，无需为切换模式重启。空白会话可以直接切换；已开始对话的会话遵循官方预设锁定规则，需要新建会话再选择。APEX 的执行保护位于独立服务作用域；共享 `run_code` 入口按会话预设分流，官方模式使用原生运行器及文件、沙箱、进程服务。更新插件代码所需的一次加载与日常模式切换是两件事。
